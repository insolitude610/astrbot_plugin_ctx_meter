# 请求体计量 (/ctx)

发一条 `/ctx`，看看这轮喂给模型的请求体到底有多大、上下文里有多少张图片。

适合上下文里有很多图片的时候使用，过多图片会导致请求体变大，影响API的首字，更可能导致连接不稳定

```

🔢 本轮最后一次调用 token：118,432（缓存输入 98,000 · 其它输入 18,000 · 输出 2,432）
```

零值的分段不会出现（没有挂工具就没有工具那一行），图片区块里的每一行也只在有内容时才出现。
把配置里的 **detail** 关掉，分段明细和整个图片区块（含图片张数与分布）都会消失，只留总字节数、
token、本轮附带的媒体数量和模型/快照时间。

### 图片为什么会分成三份

| 计数 | 来自 | 字节算在哪 |
|---|---|---|
| 历史 | `req.contexts` 里的图片块 | 落在「历史上下文」里（data URL 就是那段的绝大部分） |
| 额外块 | `req.extra_user_content_parts` 里的图片块（转发记录、空间阅读等插件注入） | 落在「额外内容块」里 |
| 本轮引用 | `req.image_urls` | **不在任何分段**（这一列只做 `len()`，不做编码） |

## 能看到哪些插件注入的内容

`/ctx` 量的是 `on_llm_request` 钩子里已经组装好的请求。按注入途径分三类：

| 途径 | 例子 | 是否算得到 |
|---|---|---|
| 框架自带（人格、技能、知识库检索、引用消息附件、system reminder） | — | 一定算得到：都在钩子之前完成 |
| `event.request_llm(...)`（`provider_request`） | `astrbot_plugin_forward_reader` 转发聊天记录、`astrbot_plugin_roll` | 一定算得到：主 Agent 在钩子之前就把它的请求取过来组装好了，与钩子顺序无关 |
| 自己挂 `on_llm_request` 往请求里塞内容 | `astrbot_plugin_qzone_reader`、`livingmemory`、`mnemosyne`、`splitter`、`llmperception` | 取决于执行顺序 → 本插件注册在 `priority = -10000`（最后执行），所以默认优先级（0）的注入都会先发生再被计量 |

最后一行是 v1.1.0 的改动：钩子顺序原本由插件加载顺序（`os.listdir`）决定，本机实测
`astrbot_plugin_ctx_meter` 排在 `astrbot_plugin_qzone_reader` **之前**，于是空间阅读注入的图文
完全没被量到；现在它一定排在所有默认优先级的钩子之后。

**仍然看不到**：优先级比本插件更低的处理器、被 `stop_event()` 中断的轮次、`plugin_set`
全局「可用插件」白名单把本插件排除的轮次、运行器里 `on_agent_begin` 追加的内容，
以及工具调用循环第 2 轮之后继续追加的内容（快照只描述本轮第一个请求）。


## 安装

把整个目录放到 AstrBot 的 `data/plugins/` 下，然后在 WebUI 插件页启用（或重启 AstrBot）。

- 需要 **AstrBot >= 4.10.0**
- 指令：`/ctx`，别名 `/ctxsize`、`/请求体`
- 全平台可用；不依赖任何平台特有接口


## 配置

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `enable` | bool | `true` | 总开关 |
| `permission_mode` | string | `everyone` | `everyone` 任何人可用 / `admin` 仅管理员 |
| `detail` | bool | `true` | 是否输出分段明细与图片区块 |
| `max_sessions` | int | `64` | 快照缓存保留的会话数上限（LRU） |
